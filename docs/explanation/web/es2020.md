# JavaScript del portal en ES2020

> **Estado:** En revisión

`apps/web/src/app.mjs` se escribe en ES2020: `const`/`let`, funciones flecha, templates, `async`/`await`, spread,
optional chaining (`?.`) y nullish coalescing (`??`). Nada posterior a 2020, ni de sintaxis ni de APIs

Es un script clásico (una IIFE), no un módulo, aunque el archivo sea `.mjs` como el resto del JavaScript del repo:
`build.mjs` lo mete inline en un `<script>` y la API inyecta `window.BYTE_PORTAL` justo antes de ese `<script>`. Con
`type="module"` el script se ejecutaría diferido y esa inyección dejaría de encontrar la etiqueta

## Por qué ES2020

El portal corre en el mini navegador que abre el sistema al conectarse a la red, antes de que el teléfono tenga
internet. Ese navegador no es Chrome ni Safari "de verdad": es el motor del sistema

- **iOS:** el Captive Network Assistant usa el WebKit del sistema, así que la versión de JavaScript es la de iOS
- **Android:** la app de inicio de sesión del portal usa el WebView del sistema, que se actualiza desde Play Store
  aparte del sistema operativo

ES2020 completo pide **iOS 14** (septiembre de 2020) y **Chrome/WebView 80** (febrero de 2020). Los teléfonos
objetivo son de 2022 en adelante: salen de fábrica con iOS 15 o Android 12 y un WebView más nuevo, así que quedan
con margen

| Motor            | Primera versión con ES2020 completo | Lo que más tarda en llegar               |
| ---------------- | ----------------------------------- | ---------------------------------------- |
| Safari / WebKit  | 14 (iOS 14)                         | `BigInt`                                 |
| Chrome / WebView | 80                                  | optional chaining y nullish (`?.`, `??`) |

### Alternativas descartadas

- **ES5 (como estaba):** ningún teléfono objetivo lo necesita, y obligaba a `var`, `function` en cada callback y
  concatenar strings. El código ES2020 es más corto y con menos trampas (`const`, scope de bloque)
- **ES2022 o posterior:** `Array.prototype.at`, `Object.hasOwn` y los campos privados piden iOS 15.4. Un iPhone de
  2022 que nunca se actualizó se queda en 15.0-15.3 y el portal fallaría justo en la pantalla de entrada, sin
  internet para actualizar nada

## Qué queda fuera

APIs y sintaxis de ES2021 en adelante, aunque el linter las sugiera en otros proyectos:

| Evitar                               | Llegó en | Usar en su lugar                       |
| ------------------------------------ | -------- | -------------------------------------- |
| `String.prototype.replaceAll`        | ES2021   | `replace` con regex `/g`               |
| `??=`, `\|\|=`, `&&=`                | ES2021   | `x = x ?? valor`                       |
| `Array.prototype.at`                 | ES2022   | `a[a.length - 1]`                      |
| `Object.hasOwn`                      | ES2022   | `Object.prototype.hasOwnProperty.call` |
| `structuredClone`                    | 2022     | copiar a mano                          |
| `toSorted`, `toReversed`, `findLast` | ES2023   | `[...a].sort()`, bucle                 |

CSS no entra en esta decisión: las propiedades nuevas se degradan solas (una regla que el motor no entiende se ignora),
mientras que una línea de JavaScript que no parsea tumba el script entero

## Cómo se valida

- **es-check** (`pnpm es-check`): `es-check es2020 apps/web/src/app.mjs --checkFeatures` falla con sintaxis o APIs
  posteriores a 2020. Corre en el pre-commit (archivos en stage), en `task check` y en CI
- **oxlint** (`.oxlintrc.json`, override de `apps/web/src`): `env.es2020`, exige `const`/`let`, templates y flechas,
  y apaga las reglas que sugieren APIs de ES2021+ (`prefer-string-replace-all`, `prefer-at`, etc.)
- El build (`build.mjs`) no transpila: lo que se escribe es lo que llega al teléfono

Si algún día el piso sube (por ejemplo a ES2022), se cambia en tres lugares: el script `es-check` de
[package.json](/package.json), el override de [.oxlintrc.json](/.oxlintrc.json) y este documento
